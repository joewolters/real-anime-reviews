# v1.10.0 "Community Hub" — GATE 0 DESIGN STUDY (PROPOSE ONLY · nothing built/changed/deployed)

Recon was run against the **live** repo (= prod, since v1.9.1 ships from this tree), then a judge-panel (4 design surfaces) + an adversarial security red-team (peer-DM / images / ban-moderation) + an ideas pass. This is the proposal; gate 1 starts after Blake answers the open questions.

## 0 · The headline (and one correction)
**You already paid for most of this backend.** The v1.9.0 cutover deployed *complete, rules-verified, indexed* schemas for `forum/{threadId}` + `posts`, `conversations/{convId}` + `messages` + `reads`, `profiles/{uid}`, `reports`, `suggestionCounts` — **with zero client UI.** v1.10.0 is mostly **giving a finished backend a face**, not building a backend. The reusable CF templates (generic `handleVoteWrite`, `recursiveDelete` cascade, `enforceRateLimit`, server-sourced `senderIdentity`, `cfProcessed` idempotency, `onUserDelete` day-1 wipe) cover most of the new server work as *bindings*, not new code.

**Correction (verify-don't-trust):** two recon agents claimed the Cloud Functions are "not deployed / half-migration." **That is a stale-banner misread.** All 13 gen-2 CFs are LIVE (the 2026-06-08 cutover ran clean; SHIP-OUTPUT history + `firebase functions:list` confirm). Counts/notifications are CF-owned in prod *today*. The deployed firestore indexes are live for the current collections; *new* queries (Hub sorts, inbox, profile reads) will need new index entries added + deployed.

**The one genuinely hard thing is not code — it's the human-moderation + legal surface** that peer DMs and image uploads open on a single manual moderator. The study treats that as the spine and proposes an honest seam.

## 1 · DATA MODEL + RULES DELTA (on top of the LIVE schema)

### Already LIVE (build the client on these, no schema work)
`comments`+`replies`, `reviews`+`threads`, votes (5 CFs), `notifications`+Lantern, `official` votes, `commentsMeta` locks, `notifPrefs`, `profiles/{uid}` (edit-form only). Per-season comments **need zero new schema** — `comments/{al:<aniListId>}/items` already inherits the wildcard rules (`communityKey()` in place).

### Already deployed as RULES-ONLY (just needs a client + a few additive clauses)
`forum/{threadId}`+`posts/{postId}` · `conversations/{convId}`+`messages`+`reads` · `reports` · `suggestionCounts` · `notifMeta`.

### NEW collections (the actual delta)
| Collection | Write | Purpose |
|---|---|---|
| `moderationGate/{uid}` | CF-only | **The rules-truth for ban + consent, folded into ONE doc** `{banned:bool, consentVersion:int}` → a single `get()` gates every community write (vs 2 reads). |
| `banned/{uid}` | CF-only | Ban audit record `{by, at, reason, cascadeCursor?}`; its create triggers the cascade. (`profiles.isBanned` stays as the human/UI mirror.) |
| `rulesConsent/{uid}` | CF-only (`acceptRules` callable) | Consent record `{version, at}` — **server-written so it can't be self-attested.** |
| `blocks/{ownerUid}/list/{blockedUid}` | owner-only, **silent** (blocked user can't read it) | Peer-DM block model (Phase B/C). `{createdAt}`. |
| `uploadState/{uid}` · `rateStatePeerOpen/{uid}` | CF-only | Per-user image byte/count limiter; tighter peer-conversation-open limiter (3/10min). |

### CHANGED on live collections (additive clauses)
- **`forum` tag enum** → add `anime:<slug>` (one value in the existing `tag in [...]`; backward-compatible) so a thread pins to a title and renders **Blake's verdict rail**.
- **`reports.targetType`** → add `'image'` (today it's missing — abusive images are literally un-reportable).
- **`conversations` update** → **remove** the participant-writable summary branch (`lastMessageText/At/unread`) — CF-only now (closes the summary-spoof + fake-unread-bomb). Participants keep only `reads/{uid}.lastReadAt`.
- **`messages` create (peer)** → extend the `state=='open'` gate so `request`/`declined`/`locked` block sends.
- **Image pointer** → an `imageRefs` string array (size ≤4, each entry must match the caller's `uploads/{uid}/` prefix) on forum-post create/update.
- **`profiles` write path** → account.js **dual-writes `profiles/{uid}`** (it writes legacy `users/{uid}` today); author-name reads flip to **profiles-first-with-users-fallback** (the fallback makes the migration safe).
- **The gate on EVERY content create+update:** prepend `&& notBanned() && hasConsented()` (one `moderationGate` read) to forum/posts, comments/replies, reviews/threads, all votes (create only — allow unvote while banned), conversations message-create, profile update. Reports stay un-gated by consent (reporting must be frictionless) but ban-gated. Admin bypasses.
- **`storage.rules`** — greenfield (see §2).

> **Net:** the rules delta is ~5 new tiny collections + ~8 additive clauses + a global `gate()` prepend. No migration of existing data. The biggest *rules* risk is the global gate touching every write rule — it gets its own gate + a full `test:rules` pass.

## 2 · CLOUD FUNCTIONS DELTA + STORAGE RULES

All new CFs **reuse the live templates** (binding, not new logic) unless noted.

| New CF | Trigger | Reuses | Owns |
|---|---|---|---|
| `onForumPostVote` / `recomputeHotScore` | `onDocumentWritten .../posts/{id}/votes/{uid}` + post create | `handleVoteWrite` (generic + `kind`), `cfProcessed` | post like counts + the **hotScore** `(up−down+0.5·postCount)/(ageHours+2)^1.5` on the parent thread |
| `setBanState` | callable (admin-literal-gated) | `alreadyProcessed` | writes `banned/{uid}` + `moderationGate.banned` + custom claim `banned:true` (instant via doc, durable via claim) |
| `acceptRules` | callable (signed-in) | — | writes `rulesConsent/{uid}` + `moderationGate.consentVersion` server-side |
| `onBanCascade` | `onDocumentCreated banned/{uid}` | `recursiveDelete` query shape, H5 redaction | **paged/resumable** tombstone of the banned user's content (`removed:true, body:'', title:''`) + lock their convos; cursor in `banned/{uid}` so it never blows the 540s budget |
| `onObjectFinalized` | Storage finalize | `enforceRateLimit` shape, `cfProcessed` | **magic-byte re-validate** (delete on mismatch — kills contentType/SVG spoof) + **EXIF strip via `sharp` re-encode** + per-uid count/byte cap |
| `onContentDelete` → Storage | post/review/comment soft+hard delete | `recursiveDelete` analogue | `bucket.deleteFiles({prefix: uploads/{uid}/{postId}/})` — closes the orphan/**legal-trap** (today a removed image stays public) |
| `onUserDelete` **extension** | (existing) | — | add `bucket.deleteFiles({prefix:'uploads/'+uid+'/'})` + a `blocks/*` sweep so "ZERO trace" is real across Storage |
| **Peer-DM trio (Phase C only):** `openPeerConversation` (callable: existence+bidirectional-block+ban+open-rate-limit → `state:'request'`), `onMessageCreate` (fan-out: send-time block re-check + `senderIdentity` + **no raw preview** + CF-owned summary), `onProfileBanned` (lock the banned user's convos) | callable / `onDocumentCreated` / `onDocumentWritten` | `senderIdentity`, `enforceRateLimit`, `cfProcessed` | the safe peer-DM substrate |

### Storage rules (greenfield — ship default-deny FIRST)
```
// storage.rules — wired via a NEW "storage" block in firebase.json, deployed BEFORE any client upload code
match /{allPaths=**} { allow read, write: if false; }                 // default-deny
match /uploads/{uid}/{postId}/{imageId} {
  allow read: if true;                                                 // public read, NO list
  allow write: if request.auth.uid == uid
            && request.resource.size <= 5 * 1024 * 1024
            && request.resource.contentType.matches('image/(jpeg|png|webp|gif)')  // SVG excluded (script-bearing)
            && firestore.exists(/databases/(default)/documents/moderationGate/$(request.auth.uid)) == false  // ban+consent gate cross-read
            ;
}
```
> **This is the gitignore↔firebase leak discipline applied to Storage:** provisioning a bucket without these rules is the leak-equivalent of a gitignored-but-not-firebase-ignored file (a class that has bitten 3×). The rules land in the *same change* the bucket is provisioned. **Recommendation: images in forum-posts ONLY for v1.10.0** (smallest blast radius); **no image DMs** (removes the CSAM-in-private-inbox vector entirely). A global **`uploadsEnabled` kill-switch** (commentsMeta-style) lets Blake disable all uploads in one admin write during an incident, no redeploy.

## 3 · THE SAFETY / ABUSE / MODERATION ARCHITECTURE (the spine)

This is the highest-risk area and the real driver of the gate plan.

### 3a · Ban is a NO-OP today (the headline gap)
`profiles.isBanned` is written by a CF but **no rule reads it** — a "banned" user keeps posting freely. Fix: a **`moderationGate/{uid}` doc-read gate** (`exists`/field check) prepended to every content write — **instant** (no token-refresh race), one `get()` per write (~$3.60 / 10M writes — negligible; the live forum rules already do a `get(parent)` per reply, so the cost shape is precedented). A **custom claim `banned:true`** rides along as durable backup. `onBanCascade` then paged-redacts backlog content + locks convos. **Apply the gate to UPDATE rules too** (else a banned user flips `removed:false` mid-cascade), and make soft-delete **monotonic** (only admin un-removes).

### 3b · Rules-consent gate (the social contract that legitimizes the ban)
A **CF-only `rulesConsent/{uid}`** (client can't self-attest) + a `CURRENT_RULES_VERSION` rules-file literal gated into every community create. **Bumping the literal re-prompts everyone** automatically on their next post. Draft copy in §4d. Recommended placement: a hard, branded modal blocking the first post/thread/DM (not a passive banner) — it's the consent record.

### 3c · Peer DMs — the honest seam (item 4)
**Adversarial verdict: peer DMs DO endanger the one-push goal** — *not* on engineering (the rules/CF work is tractable and reuses every template) but on the **human-moderation load + irreversible grooming/CSAM risk landing on a single manual moderator with no AI backstop and no age gate.** The banked "one additive clause" plan is also **wrong-shaped**: peer create must be **CF-only** (a callable), never a client `allow`-branch, so block/ban/rate checks run *before* the conversation exists.

**Recommended 3-phase split** (this is the "say so with the seam" the prompt asked for):
- **Phase A — in v1.10.0:** ship the **admin-floor "Message Blake" + suggestion-reply** channel only (already built, safe — Blake is always a party, zero stranger-to-stranger surface). The Hub gets a real DM affordance with no peer risk.
- **Phase B — fast-follow (safety infra, no new attack surface):** `blocks` model + `reports` `targetType:'dm'` + `onProfileBanned` convo-lock + the `blocks` sweep in `onUserDelete`. Pure plumbing that makes the apparatus *ready*.
- **Phase C — separate gate, on Blake's explicit go:** flip peer DMs on as **request-first, text-only, CF-created**: `openPeerConversation` callable (bidirectional block + ban + ≤3-opens/10min) → `state:'request'` → recipient gets a **content-free "X wants to message you"** ping (the first-message payload never auto-renders — defeats the unsolicited-harassment/grooming opener) → Accept = `open`, Decline = auto-block. Random `convId` (kills the social-graph existence-probe). `onMessageCreate` re-checks blocks at send. **No image DMs, ever, without their own threat model.**

### 3d · Images — CSAM is a legal event, not a moderation ticket
With no vision API + public read, any uploaded image is **world-readable and CDN-cached from finalize until a human removes it**, and propagates off-platform irreversibly. **CSAM specifically** triggers, for Blake-as-provider in the US, a **mandatory NCMEC CyberTipline report + 90-day preservation duty (18 U.S.C. §2258A)** — "just delete it" is itself mishandling — and **Google independently scans GCS and can suspend the whole project**, taking the 44 reviews offline. The minimal **non-AI** mitigation Blake accepted, made real:
1. **Lock the bucket** (default-deny rules shipped first).
2. **`onObjectFinalized`** magic-byte validate + EXIF strip + per-user cap (the only real bucket-fill defense — Storage rules can't count across objects).
3. **Atomic remove** (admin "remove image" deletes the Storage object **and** redacts the Firestore pointer — never one without the other; the redact-Firestore-only path is the legal trap) + the `onContentDelete`/`onUserDelete` Storage cascade.
4. **`'image'` report target** + a report affordance on every rendered image (the one mitigation must actually exist).
5. **A pinned runbook** for Blake: on apparent CSAM → NCMEC report + preserve to a quarantine path, then ban (a quarantine bucket reconciles the preservation duty with the deletion promise).
6. **Pre-publish friction (non-AI):** email-verified + account-age ≥ N hours before upload unlocks (raises the throwaway-account cost). **Egress is uncapped** at this gate (a viral hotlink = real money); a Cloud-Armor/signed-URL layer is explicitly deferred.

### 3e · Reports queue (extend, don't rebuild)
Clone the **suggestions admin UI**; sort by `reportCount`/recency; one-click **ban+cascade** (`setBanState`); render `snapshotText` **escape-first via `markdown.js`** (it's attacker-controlled → stored-XSS-into-admin otherwise). Add a per-reporter rate-limit + a deterministic dupe-dedupe id. **DM reports are special:** the admin can't re-fetch a private DM (H4), so `onReportCreate` server-copies the reported message + a window of context into the report doc (Blake reviews real content; disclose "reported DMs are admin-reviewable" in the privacy notice).

### 4d · Profile pages → **Direction C "Card-to-Expand, SEQUENCED"** ✅

Banned → suspended tombstone; deleted → former-member tombstone; **Blake's name → his Den** (his identity *is* the site — strongest heart protection).

**Protect-the-heart specs (bake as Playwright in `?emu=1`):** (1) a community profile/card/thread carries **NO gold token** (`#ffd54a`/`--gold*`); Blake's does. (2) **No count node** anywhere (regex digits+posts|comments|reviews|votes|likes|karma|points; no `.post-count`/`.karma`). (3) Hub `data-surface` veil resolves cozier-than-Discover but **≠ Den 0.80** (it never usurps the resting primary). (4) Blake renders a distinguishing gold marker a community member never gets. (5) banned→tombstone, deleted→graceful former-member (no dead click). (6) author-name reads `profiles` then falls back to `users` (both render, neither throws). (7) bio renders escape-first through `markdown.js` (XSS). (8) author-card mounts z-7000 above the z-6000 modal and Esc steps back without tearing down the primary.
