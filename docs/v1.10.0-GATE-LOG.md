## GATE 2 — the ban Cloud Functions. DONE (emulator-verified · STAGED · NOT deployed · NOT committed)

3 CFs that mint + manage the `moderationGate/{uid}` doc the gate-1 rules read. Cores in `functions/lib/moderation.js` (kept in sync with the rules: `CURRENT_RULES_VERSION` == `rulesVersion()`, `ADMIN_UID` == `isAdmin()`'s literal); thin `onCall`/`onDocumentCreated` wrappers in `index.js`.

### The 3 CFs
- **`acceptRules`** (callable, signed-in) — writes `rulesConsent/{uid}` + mints `moderationGate.consentVersion` **server-side** (client can't self-attest). The load-bearing one: nothing else creates the gate doc every community write depends on. Rejects a version != `CURRENT_RULES_VERSION` + an unauth caller.
- **`setBanState`** (callable, admin-literal-gated) — ban: `banned/{uid}` audit doc (triggers the cascade) + `moderationGate.banned=true` + best-effort custom claim; unban reverses all three. Rejects non-admin; refuses to ban the admin.
- **`onBanCascade`** (`onDocumentCreated banned/{uid}`) — H5-redacts (empties + `removed:true`, NOT deletes — preserves audit/report linkage) the banned user's comments/reviews/forum-threads+posts/replies, and locks their conversations. Paged (`CASCADE_PAGE=200`) + idempotent (`alreadyProcessed` + re-redact-empty is a no-op).

### Load-bearing proof
`test:cf`, real gate-1 rules enforced on a client context: fresh user comment DENIED → `acceptRules` mints `moderationGate.consentVersion=1` → same write SUCCEEDS. Rules (gate 1) + CF (gate 2) prove out together.

## GATE 3 — the "I agree" community-rules consent modal (client). DONE (verified · STAGED · NOT deployed · NOT committed)

The first visitor-facing v1.10.0 gate. A branded consent modal (no native dialog) gates every live community **create** behind `acceptRules`; a banned user gets a branded suspended state. Client-only — `firebase.js` + `script.js` + `style.css` + the practice seeder + a new spec. No rules/CF change.

### Mechanism — a server-truth pre-flight (NOT a localStorage flag)
`ensureCanParticipate()` runs before each community create: (1) bypasses the admin (uid == `NOTIF_ADMIN_UID`, mirrors the rules `isAdmin()`); (2) reads the **owner-readable** `moderationGate/{uid}`; (3) decides via the PURE `consentGateDecision(gate, version)`:
- `banned:true` → `showSuspendedModal()`, block the write.
- no doc / `consentVersion < CURRENT_RULES_VERSION` → `showConsentModal()` → "I agree" calls `acceptRules({version})` → on success the queued write proceeds (no re-click).
- else → proceed.
A per-session uid cache skips the re-read after the first confirmed consent. **Re-prompt-on-version-bump falls out for free** (consentVersion behind the literal ⇒ 'consent'); no localStorage flag anywhere.

### The 4 gated write paths (script.js)
comment create (`comments/{s}/items`), reply create (`.../replies`), review-discussion thread create (`reviews/{s}/items/{rid}/threads`), review publish (`reviews/{s}/items/{uid}`). Each: `if (!(await ensureCanParticipate())) return;` after field validation, before any optimistic UI. Forum threads + DMs aren't built yet (gates 8/18) — these 4 are the complete live community-write surface. Reports left ungated (rules: ban-gated, not consent-gated). Edit/vote paths intentionally NOT gated this gate (the SHIP-PROMPT's surface list is create-shaped; flagged for Blake as an easy extension).
