## Part D — Gate 14: image moderation + cascade + the runbook
- **`'image'` report target** + a **⚑ Report affordance on every rendered image** (the one mandatory mitigation). The report pins the exact `imagePath`; the admin queue previews the reported object + routes View to the thread.
- **Atomic remove** (`adminRemoveImage` callable + `lib/images.js`): deletes the Storage object **FIRST**, then redacts the Firestore pointer — never the Firestore-only path (the legal trap). Reachable from the reports queue and inline for admins.
- **Storage cascade**: `onUserDelete`, `onBanCascade`, hard-delete (`onForumThreadDelete`/`onForumPostDelete`), and **soft-remove** (`onForumThreadRemoved`/`onForumPostRemoved`) all sweep the right `uploads/` prefix — a removed/banned user's images actually leave Storage.
- **The NCMEC runbook**: `docs/CSAM-RUNBOOK.md` (admin-only, deploy-ignored) — plain 10-minute steps (kill-switch → quarantine-not-delete → NCMEC CyberTipline → atomic-remove → ban → log), ships regardless of the lighter upload gate.

## Storage security posture, in plain English (what stops abuse)
- **Who can upload:** only a signed-in, **email-verified**, consented, **not-banned** user, into **their own** folder, ≤5MB, real image types only (no SVG). Four images max per post.
- **What can't happen:** no one can write into someone else's folder, list/browse the bucket, overwrite a processed image, or upload a script-bearing file (SVG blocked at the rules layer; a fake "image" is caught server-side by the magic-byte check and deleted).
- **If something bad gets through:** every image has a Report button; you remove it atomically (gone from Storage AND the post in one action); a banned or deleted user's images all leave Storage; and the **kill-switch** stops all uploads instantly with one click. The CSAM runbook is the worst-case plan.
